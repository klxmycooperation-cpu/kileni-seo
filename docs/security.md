# Безопасность KILENI

Документ фиксирует реализованные границы и известные ограничения. Он не является сертификатом безопасности и должен пересматриваться после изменений API, инфраструктуры или состава данных.

## Защищаемые данные

- имена и контакты из заявок, аудитов, калькулятора и брифов;
- ответы брифов и приватные вложения;
- полный результат аудита, включая URL и технические доказательства;
- логин администратора, хеш пароля и секрет подписи сессии;
- токены Telegram и SMTP-учётные данные;
- резервные копии SQLite и вложений.

`.env` не входит в резервные копии, создаваемые `scripts/backup.mjs`. При этом сама база и вложения содержат персональные и коммерческие данные, поэтому backup нужно шифровать и ограничивать на уровне внешнего хранилища.

## Реализованные меры

### Мутации и формы

- double-submit CSRF-токен и проверка `Origin`;
- cookies `SameSite=Strict`, а административная cookie в production — также `Secure` и `HttpOnly`;
- Zod-валидация, honeypot и ограничения размера тела;
- rate limit в SQLite для форм и входа администратора;
- необязательная Cloudflare Turnstile-проверка включается только при наличии секретного ключа;
- IP и User-Agent сохраняются как HMAC, а не открытым текстом.

Доверять первому `X-Forwarded-For` безопасно только если приложение недоступно напрямую, а reverse proxy всегда удаляет входящий заголовок клиента и записывает свой проверенный адрес.

### Админка

- пароль хранится только как bcrypt-хеш;
- сессия подписана HMAC и имеет срок действия 1–24 часа;
- production-вход блокируется, если секрет сессии короче 32 символов;
- операции изменения и удаления требуют сессию, Origin и CSRF;
- вложения отдаются с `no-store`, `nosniff`, sandbox CSP и только после авторизации.

Для production рекомендуется дополнительно закрыть `/admin` VPN, SSO-gateway или IP allowlist на reverse proxy. Встроенной MFA в приложении нет.

### Загрузка файлов

- не более 5 файлов и 10 МБ суммарно;
- допустимы только PDF, DOCX, XLSX, PNG и JPEG;
- проверяются расширение, MIME и сигнатура; для OpenXML — структура ZIP;
- имя хранения — случайный UUID, исходное имя очищается;
- файлы создаются вне `public/` с правами `0600`, каталог — `0700`.

Антивирусная или CDR-проверка не реализована. Администратор должен открывать пользовательские документы в обновлённом изолированном просмотрщике; для более высокого риска нужен отдельный scanner/quarantine pipeline.

### Бесплатный аудит и SSRF

- разрешены только HTTP(S) URL без credentials и нестандартных схем;
- локальные имена, приватные, loopback, link-local и иные непубличные IP блокируются;
- DNS проверяется на каждом переходе, выбранный публичный адрес закрепляется в transport;
- редиректы ограничены и повторно валидируются;
- ограничены таймаут, размер ответа, число страниц и параллелизм;
- публичный результат хранится отдельно от полного.

На уровне инфраструктуры полезно дополнительно запретить воркеру доступ к metadata endpoints, private networks и служебным подсетям через egress firewall. Нельзя предоставлять контейнеру доступ к Docker socket.

### HTTP и браузер

`proxy.ts` добавляет CSP, `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `nosniff`, строгую referrer policy, COOP и ограниченную Permissions Policy. CSP разрешает официальный origin Cloudflare Challenges только для script/frame/connect, чтобы работал Turnstile. Текущий CSP допускает inline styles и scripts для совместимости с приложением; это слабее nonce/hash-политики и требует отдельной задачи по ужесточению.

## Секреты production

Обязательные секреты:

- `IP_HASH_SALT` — случайное значение не короче 32 символов;
- `ADMIN_SESSION_SECRET` — независимое случайное значение не короче 32 символов;
- `ADMIN_PASSWORD_HASH` — bcrypt-хеш, не пароль;
- `TELEGRAM_BOT_TOKEN`, SMTP password — только если соответствующий канал используется.

Не используйте одно значение для salt и session secret. Не передавайте секреты через Docker build args и не добавляйте `.env` в образ. Ограничьте файл `.env` правами `0600`.

## Известные ограничения

- Turnstile зависит от доступности Cloudflare; при настроенном secret проверка работает fail-closed.
- SMTP используется для ссылки на завершённый аудит и копии онлайн-брифа, но автоматического retry пока нет.
- Для неуспешной отправки Telegram нет автоматического retry.
- Worker раз в сутки удаляет только терминальные аудиты старше `AUDIT_RESULT_RETENTION_DAYS`; значение жёстко ограничено минимумом 90 дней. Восстановление после очистки возможно только из заранее созданного backup.
- Rate limit локальный и не рассчитан на несколько независимых баз.
- Нет встроенных MFA, антивируса, SIEM и автоматической ротации секретов.
- CSP пока содержит `'unsafe-inline'`.

## Эксплуатационный минимум

1. TLS завершается на доверенном reverse proxy; HTTP перенаправляется на HTTPS.
2. Внешний доступ к порту контейнера запрещён, доступен только reverse proxy.
3. Заполнены юридические данные; `PRELAUNCH_MODE=false` включается только после проверки форм и политики.
4. Настроены внешние зашифрованные резервные копии и тестовое восстановление.
5. Зависимости и базовый образ регулярно обновляются после тестов.
6. Логи не содержат токены, полные тела форм и вложения.
7. Доступ в админку и Telegram-чат пересматривается при кадровых изменениях.
