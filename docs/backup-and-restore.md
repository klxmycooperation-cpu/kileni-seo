# Резервное копирование и восстановление

`scripts/backup.mjs` создаёт согласованный SQLite snapshot через API `better-sqlite3`, копирует приватные вложения, на которые ссылается этот snapshot, и записывает manifest с SHA-256 и размерами. WAL/SHM отдельно не копируются: `database.sqlite` уже является согласованным snapshot. Если ссылочное вложение исчезло или его размер не совпал, backup завершается ошибкой и удаляет неполный каталог.

Копия не содержит `.env`, токены или другие файлы конфигурации. Она содержит заявки, контакты, результаты аудитов и вложения, поэтому является конфиденциальной.

## Формат копии

```text
kileni-backup-<UTC_TIMESTAMP>-<SUFFIX>/
├── database.sqlite
├── uploads/
└── manifest.json
```

`manifest.json` содержит UTC-время создания, версию формата, результат `integrity_check`, число вложений и SHA-256 каждого payload-файла. Все файлы создаются с закрытыми правами.

## Создать backup

В Docker, без остановки сервиса:

```bash
docker compose exec web node /app/scripts/backup.mjs
```

На хосте с установленными зависимостями:

```bash
node scripts/backup.mjs
node scripts/backup.mjs --output /путь/к/защищённому/каталогу
```

Путь по умолчанию берётся из `BACKUP_PATH`. Команда завершится с ошибкой, если исходная база отсутствует, SQLite не проходит integrity check, встречена символическая ссылка или файл нельзя прочитать.

Локальный `/data/backups` находится в том же Docker volume и защищает от ошибки приложения, но не от потери диска или хоста. После создания копируйте весь каталог backup во внешнее версионируемое хранилище с шифрованием, проверкой доступа и отдельной политикой retention.

## Проверить копию

Скрипт проверяет snapshot при создании. Для независимой проверки сравните перечень и SHA-256 с `manifest.json`, затем откройте копию SQLite в read-only режиме и выполните:

```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

Не считайте backup проверенным, пока не выполнено тестовое восстановление в отдельное окружение и не открыты несколько записей и вложений.

## Восстановить

Восстановление заменяет текущую базу и каталог вложений, поэтому возможно только с явным `--confirm`. Сначала остановите оба сервиса:

```bash
docker compose stop worker web
docker compose run --rm --no-deps web \
  node /app/scripts/restore.mjs /data/backups/<КАТАЛОГ_КОПИИ> --confirm
docker compose up -d
```

На хосте:

```bash
node scripts/restore.mjs /путь/к/kileni-backup-... --confirm
```

Перед заменой restore:

1. Проверяет формат manifest, состав файлов, размеры и SHA-256.
2. Выполняет `PRAGMA integrity_check` для восстанавливаемой базы.
3. Если текущая база существует, автоматически создаёт отдельный pre-restore backup в `BACKUP_PATH`.
4. Готовит базу и вложения во временных каталогах.
5. Меняет их через rename и откатывает swap при ошибке.
6. Повторно проверяет установленную базу.

После запуска проверьте `/api/health`, логи web/worker, вход в админку, несколько записей, скачивание вложения и постановку тестового аудита.

## Рекомендуемая политика

- ежедневный автоматический backup;
- отдельная копия вне основного хоста;
- шифрование при передаче и хранении;
- ограниченный сервисный аккаунт для backup;
- период хранения, согласованный с политикой персональных данных;
- ежемесячное тестовое восстановление;
- журнал даты, размера, результата integrity check и теста восстановления.

Секреты из `.env` резервируются отдельным механизмом менеджера секретов. Не добавляйте их в каталог backup ради удобства.
