# План исправлений по итогам полного аудита

Дата: 4 сентября 2026 года. Приоритет — минимальные доказанные изменения с максимальным эффектом. Принятые отчёт, PDF, выборка, CTA, цены, тексты и дизайн-концепция заморожены.

## Выполнено в preview

### P1. Тяжёлые изображения и неправильный приоритет загрузки

**Доказательство:** production Lighthouse и network trace показывали примерно 2,29 МБ на главной и 2,20 МБ на статье; исходные PNG около 1,8 МБ загружались раньше, чем требовалось. Статья имела mobile LCP около 20,6 с в медиане трёх запусков.

**Минимальное исправление:**

- подготовлены локальные WebP без изменения визуального сюжета;
- изображения карточек вне первого экрана переведены на lazy loading;
- hero статьи помечен как приоритетный LCP-ресурс (`fetchPriority=high`, eager);
- внешний вид, размеры блоков и accepted intro не менялись.

**Критерий:** transfer weight снижен примерно до 0,41–0,50 МБ, desktop TBT равен 0 мс, изображение статьи имеет priority hint. Выполнено.

**Финальная внешняя проверка изолированного preview:** три HTTPS-запуска для каждого профиля. Главная — mobile 91 / LCP 3,12 с / TBT 54 мс, desktop 99 / LCP 0,84 с / TBT 0 мс. Статья — mobile 93 / LCP 2,72 с / TBT 31,5 мс, desktop 95 / LCP 0,85 с / TBT 0 мс. Подтверждённый TBT-дефект уровня P1 после исправления не воспроизводится. Остаточные mobile LCP главной/статьи и CLS брифа не скрываются и перечислены ниже как P2.

**Откат:** вернуть прежние ссылки на PNG и атрибуты загрузки в `ArticlesPage`/`HomeArticleCarousel`; WebP-файлы можно оставить как неиспользуемые до отдельной очистки.

### P1. Desktop `<details>` визуально открыты, семантически закрыты

**Доказательство:** before screenshot и DOM/accessibility tree страницы `/about`: CSS показывал содержимое, но native `<details>` не имели `open`, поэтому клавиатура и screen reader не получали тот же результат, что зрячий пользователь.

**Минимальное исправление:** компонент `AboutDisclosure` синхронизирует `open` с desktop media query; на mobile disclosure остаётся управляемым пользователем.

**Критерий:** desktop — четыре блока реально открыты и summary скрыты; mobile — изначально закрыты и раскрываются нажатием. Выполнено в настоящем браузере.

### P1. Нарушение порядка заголовков в брифе

**Доказательство:** Axe `heading-order` moderate и отдельный red regression test.

**Минимальное исправление:** добавлен смысловой visually-hidden H2 над H3-контентом guide-блока. Макет и текст для пользователя не менялись.

**Критерий:** targeted Chromium/WebKit и итоговый Axe не показывают moderate/serious/critical. Выполнено.

### P1. Недостаточный контраст в темах и mobile-состояниях

**Доказательство:** исходный production Axe-проход воспроизвёл serious `color-contrast` на `/services`, `/seo`, `/glossary/lighthouse`, `/checks/http-status`, `/contacts`, а в mobile-сценариях также на `/`, `/pricing` и `/services`. Дефект повторялся в Chromium и WebKit.

**Минимальное исправление:** скорректированы только цвета второстепенного текста, подписей и состояний в существующих темах; для светлых SEO/glossary/checks-страниц добавлены узкие scopes хлебных крошек. Структура блоков и принятая визуальная композиция не менялись.

**Критерий:** основная матрица из 36 browser/Axe-сценариев и расширенная матрица из 84 сценариев не содержат serious/critical, horizontal overflow, console errors и page errors. Выполнено в Chromium и WebKit на desktop/mobile, Dark/Signal/Light; доказательства — `accessibility/summary.json`, `accessibility-final/summary.json`, `contrast-before-production-20260905/` и `contrast-after-preview-final-20260905/`.

### Ошибки движка бесплатного аудита

Исправлены в той же preview-ветке, потому что каждый дефект воспроизводился controlled fixture:

- non-self canonical больше не означает «подтверждённый дубль» без совпадения содержимого/redirect/alias;
- классификация login/account опирается на сильные наблюдаемые признаки;
- основная локаль и разные типы страниц выбираются раньше alternate copy;
- terminal state сохраняется атомарно и не перезаписывается поздним событием;
- API/web/PDF/admin строятся из одного сохранённого client snapshot;
- hreflang применяется только когда для конкретной страницы реально обнаружена языковая пара или сохранена языковая разметка;
- noindex выбранной публичной utility/conversion-страницы больше не скрывается из findings и карточки URL;

### Профилактическое усиление, не связанное с fixture-дефектами

Эти изменения не выдаются за ошибки движка бесплатного аудита:

- admin login сохраняет существующую проверку лимита до bcrypt; отдельные тесты подтверждают, что успешный вход очищает счётчик и что secure-cookie корректно работает на HTTPS, а localhost-сценарий не получает неподходящий secure-флаг;
- metrics API — отдельная продуктовая функция минимальной статистики, а не исправление fixture: она принимает только нормализованный публичный path и ограничивает объём и срок хранения данных;
- standalone packaging — release hygiene: подготовка runtime удаляет устаревшие `.enc`, проверяет имена environment-файлов, приватные ключи и не включает secrets.

## Не исправлять автоматически

### Accepted intro и first-visit LCP

Первое мобильное посещение остаётся дороже возвращающегося из-за утверждённой бренд-анимации. В финальном внешнем preview LCP главной превысил 2,5 с в двух из трёх mobile-запусков (1,94 / 3,20 / 3,12 с). Пользователь ранее потребовал сохранить скорость и постоянное появление анимации. Это продуктовый компромисс, а не разрешение самовольно упростить intro. Решение — отдельное согласование: сохранить как есть, сократить длительность или считать intro частью осознанного опыта.

### Остаточный mobile LCP статьи

После сокращения веса изображений mobile LCP статьи составил 2,75 / 2,72 / 2,71 с: три запуска остаются выше 2,5 с, хотя TBT стабильно низкий. Это P2, а не основание для нового редизайна. Следующий разумный шаг — проверить полевые Core Web Vitals и только затем локализовать оставшийся LCP-путь.

### Mobile CLS брифа

Во внешнем preview CLS брифа равен 0,11 во всех трёх mobile-запусках. Browser QA не показал заметного скачка или overflow, поэтому исправление без воспроизводимого элемента было бы спекулятивным. Нужен отдельный trace/layout-shift сценарий либо полевые данные.

### Старый TBT кейса и статьи

На production превышение 200 мс подтвердилось у кейса в трёх из трёх запусков, у статьи — в двух из трёх. Во внешнем preview оно не повторилось ни разу. Отдельная единственная причина старого TBT не доказана, поэтому не добавлялась спекулятивная оптимизация. После будущего production deployment нужно повторить те же три mobile-запуска; публикацию нельзя считать окончательно подтверждённой без этого замера.

### Два redirect-hop для `http://www`

Все варианты безопасно доходят до канонического HTTPS. Оптимизация Caddy до одного hop полезна, но не блокирует релиз и затрагивает production-конфигурацию. Выполнять только отдельной командой с проверкой сертификата и откатом Caddyfile.

### Axe minor `aria-allowed-role`

Сценарии клавиатуры и screen-reader names работают, serious/critical нет. Замена семантических контейнеров возможна отдельно; в финальный P1-pass не включена.

### BreadcrumbList и тексты

Не добавлять без реальной иерархии. Не переписывать client report, PDF, цены, CTA и product copy без нового воспроизводимого дефекта.

## Последовательность выпуска

1. Завершить unit/integration, build, packaging, Chromium и WebKit.
2. Развернуть отдельный Timeweb preview с отдельной БД, worker и noindex. Выполнено; после обнаружения наследованных production-переменных стенд повторно изолирован на SQLite, Turso/SMTP/Telegram/Turnstile отключены.
3. Проверить внешний preview: health, noindex, home/article assets, `/about`, `/brief`, free-audit pipeline, PDF/admin parity. Выполнено на новом cache-miss snapshot: web/PDF/admin client model имеют одинаковый SHA-256, текст двухстраничного PDF и все десять URL сверены отдельно.
4. Сохранить after screenshots и обновить regression report. Выполнено.
5. Production не менять.
6. Для будущего production release создать новый release-каталог, переключить symlink/compose только после команды владельца; предыдущий release оставить для мгновенного rollback.

## Release blockers

Обязательные блокеры до production:

- любой красный unit/integration/E2E/build;
- отсутствие no-secrets packaging проверки;
- внешний preview использует старые PNG или старый runtime;
- расхождение API/web/PDF/admin;
- невозможность завершить бесплатный аудит или открыть результат;
- missing evidence по Chromium/WebKit/visual QA;
- не выполнена реальная доставка письма на контролируемый внешний адрес.

### Обязательный post-deploy smoke

Сразу после будущего переключения production выполнить по три одинаковых mobile Lighthouse-запуска для главной, кейса и статьи. Если кейс или статья снова получают TBT выше 200 мс минимум в двух из трёх запусков, либо перестаёт работать health/audit flow, новый release не считать принятым и вернуть предыдущий runtime. LCP первого входа на главной не является условием отката сам по себе: текущая утверждённая intro-сцена осознанно влияет на этот показатель и требует отдельного продуктового решения.

Не являются блокерами сами по себе: `http://www` в два hop, Axe minor, accepted intro tradeoff и отсутствие Search Console/analytics access — они должны быть явно задокументированы.
